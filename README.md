# MenuAI 料理写真の合成エンジン

スマートフォンで撮った料理の写真を、背景をきれいに整えたメニュー用の画像に変換するエンジンです。

- 料理の部分だけを切り抜き、用意した背景デザイン（テンプレート）の上に置きます。
- 影と色味を整えたあと、「料理の見た目が変わっていないか」を自動でチェックします。
- **料理そのものを AI で描き直すことはしません。** 写真に写っている料理がそのまま使われます。

![入力写真と、同じ料理を3種類の背景に合成した結果](docs/images/hero.jpg)

<sub>左が入力写真、右の3枚が合成結果です（背景: `T01_warm_ivory`、`T04_dark_premium`、`T05_japanese_editorial`）。写真の出典: [docs/images/CREDITS.md](docs/images/CREDITS.md)</sub>

## このリポジトリについて

MenuAI は 2 つのリポジトリでできています。

| リポジトリ | 役割 |
|---|---|
| **menu-ai-service**（ここ） | 画像を処理する AI サービス（Python / FastAPI） |
| [menu-ai](https://github.com/doromi22/menu-ai) | お店の人が使う Web アプリ（Laravel）。写真を受け取り、このサービスに処理を依頼します |

## AI コーディングツールの利用について

実装の大部分は AI コーディングツール（Claude Code）を用いており、
コミットの Co-Authored-By に記録している。

自分が担当したのは以下である。

- アーキテクチャの決定（ADR パターンの採用、Web 層と AI 層の分離）
- ビジネスルールの定義と、その整合性の検証
- モデル選定とトレードオフの判断（BiRefNet の採用、生成 AI を採らない判断）
- 景品表示法上のリスクを踏まえた仕様の決定
- リファクタリングの方向づけとレビュー

コードの各行を自分で書いたとは主張しない。

## なぜ画像生成 AI を使わないのか

最初の試作（`main.py`、`modal_app.py`）では、画像生成 AI（SDXL）で背景を作っていました。
ただ、メニュー写真を見たお客様は、その写真のとおりの料理が出てくると思って注文します。画像生成 AI は、量やトッピング、質感を知らないうちに変えてしまうことがあり、実物と違う写真になるおそれがあります。

そこで、`standard/` にある **Standard パイプライン**では、AI に絵を描かせるのをやめました。写真から料理を切り抜いて貼り合わせるだけの、毎回同じ結果になる処理にしています。GPU も必要ありません。
画像生成 AI を使う方式は、明示的に選んだときだけ動く `premium` モードとして残しています。

## 処理の流れ

![処理の流れ: 写真 → 切り抜き → 配置 → 影 → 色補正 → 背景と合成 → 改変チェック → 画像とメタデータ](docs/images/pipeline.svg)

| # | ステップ | やること | コード |
|---|---|---|---|
| 1 | 切り抜き（Segmentation Gate） | BiRefNet というモデルで料理の範囲を見つけ、使える写真かどうかを判定します | `standard/segmentation/` |
| 2 | 配置（Layout） | 切り抜いた料理を画面のどこに置くかを決めます | `standard/layout/` |
| 3 | 影（Shadow） | 料理の下に自然な影を付けます | `standard/shadow/` |
| 4 | 色補正（Color Grade） | 明るさや色味を控えめに整えます | `standard/color/` |
| 5 | 合成（Template Render） | 背景デザインの上に、影と料理を重ねます | `standard/templates/` |
| 6 | 改変チェック（Integrity Check） | 実際に保存される画像（JPEG 圧縮後）を見て、料理が変わりすぎていないかを 4 つの観点で確認します | `standard/validator/` |

**判定は 3 種類です。**

- **PASS**: そのまま使えます。
- **REVIEW**: 画像は作れましたが、人の目で確認したほうがよい状態です（例: 料理が写真の端にかかっている）。
- **REJECT**: 使える画像を作れません（例: 料理がほとんど写っていない）。

判定には、理由を表す「理由コード」（例: `SEGMENTATION_BOUNDARY_TOUCH_EXCEEDED` = 料理が写真の端に接しすぎている）が必ず付きます。どの理由で REVIEW が多いのかを、あとから集計できるようにするためです。

そのほかの仕組みは次のとおりです。

- **しきい値の管理**（`standard/policy/`）: 「どこからを REVIEW にするか」といった基準値は 1 つの YAML ファイルにまとめています。ファイルの内容からハッシュ値を計算してレスポンスに記録するので、どの基準で判定された画像なのかをあとから確認できます。
- **作り直し（リトライ）**（`standard/retry/`）: **コンピューターが自分で判断して直せるものだけ**を作り直します。今は「色が元の写真より鮮やか・明るくなりすぎた」ときだけで、色補正を弱めて最大 2 回作り直し、それでも直らなければ人の確認（REVIEW）に回します。配置や細部の変化は、作り直して良くなったかをコンピューターが判断できないため、最初から人に任せます。完璧を目指して仕組みを複雑にするより、判断できる範囲に絞るという方針です。
- **障害時の扱い**: モデルの読み込み失敗など、写真ではなくサーバー側に原因がある失敗は、`is_infra_error` で区別します。「写真が悪い」と誤って伝えないためです。この場合の再実行には、回数だけでなく時間の上限（20 秒）も設けています。1 回の推論に 30 秒以上かかることもあるため、回数だけで制限すると Web アプリ側のタイムアウト（60 秒）を超えてしまうからです。
- **テストハーネス**（`mvp_harness/`）: たくさんの写真 × 6 種類の背景をまとめて処理し、カテゴリ別・背景別の合格率を表にします。

## 実際の写真で見つかった問題と、その直し方

作ったばかりの合成テスト用の画像では問題ありませんでしたが、実際の飲食店の写真を使うと、次の 3 つの問題が見つかりました。

1. 器の一部が欠ける
2. ラーメンの海苔が消える
3. 箸の輪郭がギザギザになる

### 問題 1・2: 器や海苔が消える → 原因はモデルだった

最初はプログラムの不具合を疑いました。そこで、判定をする前の「モデルがそのまま出した結果」を画像にして確認しました。すると、欠けている部分はその時点ですでに消えていました。つまり、あとの処理をいくら直しても取り戻せない、**モデル自体の限界**でした。

そこで、商用利用できる MIT ライセンスのモデル（BiRefNet の 3 種類）を、問題が起きた写真で比べました。候補だった BRIA RMBG 2.0 は、商用利用できないライセンスだったため最初から外しています。

- `birefnet-dis`: 1 枚は良くなったものの、別の写真では器が丸ごと消えてしまいました。
- **`birefnet-hrsod`**: 新しい失敗を出さずに、問題の写真を改善できました。→ **これを採用しました。**

比べた結果の詳細は [`standard/segmentation/README.md`](standard/segmentation/README.md)（英語）にあります。

| 前のモデル（`birefnet-general`） | 採用したモデル（`birefnet-hrsod`） |
|---|---|
| ![器が消えている](docs/images/model_general.jpg) | ![器が戻っている](docs/images/model_hrsod.jpg) |
| 器が丸ごと消えて、料理だけが浮いています。 | 器は戻りました。ただ、ソースの容器や隣の器まで一緒に切り抜かれています。 |

右の画像のとおり、新しいモデルは広めに切り抜く分、料理の近くにある小物も一緒に入ってしまいます。これはモデルを変えたことによる**トレードオフ**です。

ラーメンの写真では、モデルを変えたあと**合格率が 92% から 77% に下がりました。** 1 枚ずつ原因を調べると、切り抜きが悪くなったわけではありませんでした。前のモデルは大きな海苔 2 枚を気づかないうちに消していて、新しいモデルが正しく海苔を残した結果、切り抜いた範囲が写真の上端に届き、「端に接している」チェックが正しく反応していたのです。
**バグを直したことで、そのバグに隠れていた問題が見えるようになった**、というケースでした。

### 問題 3: 輪郭がギザギザになる → 原因は合成の処理だった

モデルは料理の境目を 0〜1 のなめらかな値（アルファ）で出しています。ところが、判定のためにこれを「料理か、料理でないか」の 2 値（マスク）に変換し、合成でもそのマスクをそのまま使っていました。そのため、境目のなめらかさが失われ、斜めの輪郭が階段状になっていました。

そこで、**合成するときだけ**、境目の細い帯の部分に元のなめらかな値を使うようにしました。料理の内側はこれまでどおり完全に不透明なので、スープが透けて見えることはありません。
切り抜きの判定には今までの 2 値マスクを使い続けています。ラーメンの写真では、この修正で **78 件の判定結果は 1 件も変わりませんでした。**

ただし、改変チェックは「実際にできあがった画像」の色を測るため、判定が変わる写真もあります。輪郭の内側の数ピクセルが背景の色と混ざるので、明るい背景では色が少し薄く測られます。たとえば `donburi_010` は、明るい背景（`T01`）では REVIEW から PASS に変わり、暗い背景（`T04`）では REVIEW のままでした。

| 修正前 | 修正後 |
|---|---|
| ![ギザギザの輪郭](docs/images/edges_before.png) | ![なめらかな輪郭](docs/images/edges_after.png) |

## 実際の写真での結果

| カテゴリ | 写真の枚数 | 合格率 | REVIEW | REJECT |
|---|---|---|---|---|
| デザート | 14 | **100%** | 0 | 0 |
| パスタ | 14 | 79% | 12 | 6 |
| ラーメン | 13 | 77% | 18 | 0 |
| 丼もの | 12 | 75% | 18 | 0 |

- 数は「写真 × 背景 6 種類」の件数です。たとえば REVIEW の 18 件は、写真 3 枚分（3 × 6）にあたります。全体の合格率は 83%（318 件中 264 件）です。
- REJECT は、お皿の縁が写らないほど近づいて撮った写真 1 枚だけで、使えない写真として正しく判定されています。
- 色が鮮やかになりすぎた写真 2 枚は、作り直し（リトライ）で自動的に直りました。作り直しは 9 件で動き、9 件とも PASS になっています。
- 残っている REVIEW の理由は、料理が写真の端にかかっていること（いちばん多い）、麺のすき間が穴として判定されたこと、定食のトレーで主役の料理を決められなかったことです。どれも人が見て判断するべきものです。
- ラーメンの写真は出どころを確認できていないため公開していません。そのほかは、ライセンスを確認した Wikimedia Commons の写真です（`scripts/collect_test_photos.py` で集め、ファイルごとのライセンスも記録しています）。

**処理時間**（GPU なし、CPU のみ）: 1 回のリクエストで約 6〜12 秒です。テストハーネスでは、1 枚の写真を 6 種類の背景で処理して約 14 秒です（大きな写真の場合の中央値）。
以前は背景ごとに切り抜きをやり直していて 42.7 秒かかっていましたが、1 枚につき 1 回だけ切り抜くように直しました。

## まだできていないこと

- **小物まで切り抜かれる**: 新しいモデルは、紙ナプキンやソースの容器、隣の器を一緒に切り抜きやすくなりました。
- **器が欠ける問題は、減ったものの残っています**: ガラスの器や一部のお皿は、まだ抜け落ちることがあります。
- **写真の端でまっすぐ切れる**: 写真の端にかかっていた料理を真ん中に寄せると、もともと写真の外だった部分が直線で切れて見えます。
- **料理の役割を判別できない**: 今は「いちばん大きいもの = メインの料理」としています。そのため、定食のトレーは REVIEW になります。
- **背景デザインの数値**: 仕様書で数値が決まっているのは `T01_warm_ivory` だけで、`T02`〜`T06` は仮の値です。
- **大きな写真では輪郭が少しやわらかく見える**: 3024×4032 のような大きな写真を 100% で見ると、輪郭が少しやわらかく見えます。モデルが約 1024px の大きさで判断しているためで、わざとぼかしているわけではありません。

## 動かし方

**準備**

```bash
python -m venv venv && ./venv/Scripts/python.exe -m pip install -r standard/requirements.txt
```

**テスト**

```bash
./venv/Scripts/python.exe -m pytest                      # 185 件。モデルのダウンロードは不要です
./venv/Scripts/python.exe -m pytest -m integration       # 本物のモデルで推論します（初回は約 1GB をダウンロード）
```

**起動と実行**

```bash
./venv/Scripts/python.exe -m uvicorn standard.api.main:app --port 8002    # Web アプリから呼ばれる API サーバー
./venv/Scripts/python.exe -m mvp_harness photos/ramen photos/out           # フォルダ内の写真をまとめて処理
./venv/Scripts/python.exe scripts/build_readme_assets.py                   # この README の画像を作り直す
```

まとめて処理するときは、ファイル名の先頭にカテゴリ名を付けてください（例: `ramen_001.jpg`）。
写真、処理結果の画像、モデルのファイルはリポジトリに含めていません。

## フォルダ構成

```
standard/        Standard パイプライン本体（切り抜き、配置、影、色補正、背景、チェック、リトライ、基準値、API）
mvp_harness/     写真 × 背景をまとめて処理し、合格率の表を作るツール
scripts/         写真の収集、モデルの比較、調査用スクリプト、README の画像作成
docs/            Web アプリとの通信の仕様、レスポンスの JSON スキーマ
main.py, modal_app.py   最初に作った、画像生成 AI を使う方式（Premium）の試作
```

コード中のコメントと、フォルダごとの README は英語です。仕様書（韓国語）の文章をそのまま引用している箇所があります。
